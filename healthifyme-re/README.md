## Sync engine (observed: decompiled via REA/JADX — dx.m0, u90.m, services.c/o, SyncLogsWorker)
**Two generations coexist**
1. *Legacy per-entity sync tokens* — `foodlog/foodlog_sync/`, `users/me/workout_log/workoutlog_sync/`, `water_tracking/sync/`, `users/points_log/sync/`, `objectives/sync/`, `sleep_log/sync`, `body_measurement/logs/sync/`, `group/sync/`, `user/budgets/sync`: client sends dirty rows + last `sync_token`; server returns `{updates[], sync_token}`
2. *Unified table protocol* — `GET/POST user_sync/data?table_names=<T>&install_id&device_id[&sync_mode][&force_sync][&sync_type=reverse]`; POST body `{device_id, data:[{table_name, rows:[…]}]}`, GET → `{data:[{<T>:[rows]}], next_page}` (paged). Tables seen: RawWorkoutLog, AggrWorkoutLog, RawWaterLog, CGMLogs, CGMOffsets, UserMealPreferences, UserCustomFastingLogs, UserReminder, … `sync_type=reverse` + `force_sync=true` = full restore from server (reinstall/new device). Rows keyed by client `record_id`/`local_id`/`app_local_id`; server echoes `{app_local_id, id}` to bind server IDs. Plus `/api/v1/tracker/sync-wrapper` {sync_token, device_id, updates} for newer trackers
**Food-log push (dx.m0.k)** — collects dirty FoodLogEntry lists (deletes, updates, inserts) → each row JSON: `local_id, server_id(-1 if new), food_id, quantity, calorie_value, measure_weight, entry_time(diary date), meal_type, meal_subtype, food_measure_to_weight_map_id, food_name, isdeleted, source:"N", log_source, device_log_time, consumed_at` → envelope `{install_id, sync_token, food_logs:[…]}` (token = stored server token, or now-epoch-seconds on first sync) → `POST foodlog/foodlog_sync/?source=online_track&token=…`
**Apply response (u90.m.a0 → services.o.e)** — for each server update: find local row by `server_id = ? OR (_id = ? AND install_id = ?)`
- no match → INSERT (entry from server/other device)
- match & local `timestamp <= syncStart` → UPDATE (by server_id, or by local id+install_id → binds server id)
- match but local row edited after sync started → skip (local edit stays dirty, wins next round)
- id collision from another install → skip + log
Then persist new `food_log_sync_token`, broadcast `ACTION_FOOD_LOG_SYNC_COMPLETED`, chain meal-preference sync if updates arrived. ⇒ **server-wins, except edits made during the in-flight request**; deletes are soft (`isdeleted`) so they propagate. Possible unit mismatch (local `timestamp` set via strftime('%s') seconds vs `System.currentTimeMillis()`) could make the guard always pass — unverified.
**Triggers** — `SyncLogsWorker` (WorkManager, enqueued from DashboardActivity; requires signed-in + network, else `Result.retry()` backoff) fans out to food-log, workout-log, weight, reminder & uninstall-ping syncs; "online_track" path pushes right after logging; ~30 legacy IntentService/JobIntentService syncers (Profile, WeightLog, WorkoutLog, ExpertConnect, RefreshEverything) + FCM-triggered refresh; Health Connect helpers (activity, steps, sleep, hydration, weight, vitals, blood glucose) import into local tables then ride the same sync

## CGM / Libre sensor (observed: NfcVReaderTask.k decompiled; models via dexann.py)
**Sensors** — `SensorType`: LIBRE_PRO, LIBRE_PRO_H (optimized-scan variant), LIBRE_US_14DAY (Libre-1-family, NFC-V/ISO 15693, unencrypted FRAM); DEXCOM_STELO also listed (no NFC path seen — likely via Health Connect `HealthConnectBloodGlucoseSyncHelper`; inferred). No Libre 2/3 BLE protocol code found
**Scan pipeline** (`basic.cgm.libre1.NfcVReaderTask`, AsyncTask on NFC tag discovery)
1. `NfcV.connect()` → read patch info → `SensorType` detect → reject if not in allowed list from server config (`READ_FAIL_INVALID_SENSOR`)
2. Serial number derived from tag UID; if differs from stored sensor → `READ_NEW_SENSOR_DETECTED` (sensor replacement flow, `POST /api/v1/user/sensor/replace/` {device_id, device_type, replacement_reason, replacement_type})
3. Block-read full FRAM (`me0.b`, timeout → `READ_FAIL_TIMEOUT`) → CRC check (`READ_FAIL_CRC_FAILED`)
4. State byte `fram[4]` → SensorState: NOT_ACTIVATED (app performs activation command, then warming up) / WARMING_UP / ACTIVE / EXPIRED / SHUTDOWN / FAILURE → mapped to CGMSensorState and persisted via `user/sensor/` {device_id, device_type, device_model, device_status}
5. `ne0.b` wraps raw FRAM + parse helpers (sensor age minutes, trend/history ring indices, raw words) → stored locally in Room `sensor_raw_data` (raw BLOB + patch_info) as offline queue
**Glucose conversion is server-side** — `POST /iot/api/v1/cgm/libre-1/calibrate` {sensor_id, sensor_memory (encoded FRAM), sync_timestamp, time_offset_in_minutes} → `CGMLogs[]` {local_id, sensor_id, sensor_model, age_in_sensor_minutes, glucose_level_mgdl, raw_glucose, calibrated_glucose, utc_datetime, tz offset} → Room `glucose_data`; also `POST cgm/log_raw_data` {sensor_memory, patch_info, sensor_model, last_synced_sensor_age_in_minutes} (raw archive). ⇒ proprietary calibration algorithm lives on the backend ("iot" service), not in the APK
**User calibration offsets** — Room `cgm_offset` {created_at, offset_value, sensor_device_id} + feedback, synced via `user_sync/data?table_names=CGMOffsets`; readings sync via `table_names=CGMLogs`
**Analytics (server)** — `GET /api/v1/cgm/scores?date` → per-day metabolic_score, time_in_target, avg_glucose, glucose_variability (each value + delta vs previous day), hba1c_info (estimate + lab booking CTA), ria_insights cards; `GET /api/v2/cgm/predictive_glucose_graph` → series {predicted_value, lower/upper bound} (forecast band); `cgm/config` → ideal/average ranges, colouring rules, variability bands, cards order (server-driven UI); `cgm/tracker-tagging/*` → tag glucose spikes with meals/images/notes (food↔glucose correlation), `cgm/event-history` search

## Smart scale (observed: QN SDK classes, libyolanda_calc JNI exports, SmartScaleSheetActivity.e.x + YolandaHelper decompiled)
**Hardware/SDK** — HealthifyMe-branded **Lifetron** BIA scale (`DeviceModelEnum.LIFETRON`), driven by the vendored **QN (Qingniu/Yolanda/Kingnew) Android SDK**: public API `com.qn.device.out` (QNBleApi, QNBleDevice, QNUser, QNScaleData, QNScaleItemData; also height-scale, ruler/tape, kitchen-scale, Wi-Fi & OTA configs unused here), internals `com.qingniu.*` (BLE scanner/blemanage, scale models, slim-scale structs). Native: `libyolanda_calc.so` (44 JNI exports — `MeasuredDataCalc`/`BleScaleData`: initWithWeight/Athlete, calcBmi, calcBodyShape, calcHeartIndex, calc{Specialty,Professional,KalmanSpecialtyV2,QuadElectrode}BodyData, encrypt/decrypt/calibrate resistance) + `libylpacker.so` (pack/unpack BLE frames)
**Flow** (`smart_scale.presentation.activity.SmartScaleSheetActivity`, bottom-sheet UI states via `SmartScaleEnum`)
1. Bluetooth permissions → QNBleApi scan (BLE) → connect to QNBleDevice; `QNUser` built from profile (height, gender, DOB) — required because BIA body-comp formulas depend on them
2. Scale streams live weight (`z(device, double)` callback) → stable reading → SDK computes body composition **on-device** from weight + bio-impedance via libyolanda_calc
3. `onGetScaleData(device, QNScaleData)` → if ≥1 item: `YolandaHelper.a()` maps QN item-type IDs (2–31, ~24 metrics: body fat %, BMI, muscle mass, skeletal muscle, bone mass, body water, protein, BMR, visceral fat, subcutaneous fat, body age, fat-free mass, heart rate, body shape, score, …) → `SmartScaleData` cached in `SmartScalePref` (SharedPreferences)
4. First successful reading: device state NOT_RECEIVED → ACTIVATED; registers sensor via `POST user/sensor/` {device_id=MAC, device_type=WEIGHING_SCALE, device_model=LIFETRON, device_status}
5. Success screen (`SmartScaleSuccessFragment`, shareable image) → weight/body-measurement logs (`body_measurement/logs/bulk_upload`, `weightlog` table) → dashboard `SmartScaleCardView`; analytics `mx0.a` success/failure
- Unlike CGM, **all body-composition math is local** (vendor native lib); server only receives final metrics
